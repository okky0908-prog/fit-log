# テスト計画書

[要件定義書](./requirements.md) の詳細ドキュメント。FIT LOG の自動テストを、どの層で・どの技法で・どんなケースを作るかを決める。

前回の SNS アプリは、できあがったコードにあとからテストを足した（段階ごとにカバレッジを上げた）。今回は**最初からテスト駆動（TDD）で作る**ので、この計画書は「機能を作る PR ごとに、どの技法でケースを洗い出し、どこまで確かめれば完了か」の決まりとして使う（[CLAUDE.md](../CLAUDE.md)「テスト駆動開発（TDD）のルール」）。

## 1. 目的と範囲

| 目的 | 内容 |
|---|---|
| 壊れていないことを自動で確かめる | 毎回ブラウザで手で確かめなくても、`./gradlew check` と `npm test`・`npm run test:e2e` で分かるようにする |
| 変更の安全網にする | 機能の追加・整理・ライブラリの更新のあとに、動きが変わっていないと言えるようにする |
| 仕様を記録する | テストの名前と中身を読めば、仕様（境界・エラーの条件・計算の決まり）が分かるようにする |
| 非機能要件を確かめる | [要件定義書 7章](./requirements.md) の「テストで確かめる」とした項目（閲覧の制御の漏れ・健康情報を本人以外に出さない・単位の換算で値がずれない・日付の区切り・アカウントの安全）を、機能のテストとは別に、横断の観点（[4章](#4-このアプリで横断して確かめる観点)）として確かめる |

- 対象：バックエンド（計算のクラス・DB アクセス・Service・Controller・結合）、フロントエンド（関数・通信・UI 部品・画面）、E2E（画面とサーバーをつないだユースケース）
- 対象外
  - 性能・負荷のテスト：CI で毎回は動かさない。非機能要件で数値を決めたあと、パフォーマンステスト計画書（`performance-test-plan.md`。AWS へのデプロイの前に作る）で扱う。ただし「一覧の API で SQL の数が件数によらず同じ（N+1 がない）」ことは、機能のテストで毎回確かめる（[4.7](#47-n1-がないこと)）
  - AWS 上の環境（SES・RDS・S3 の本物）。手元と CI では、Mailpit・使い捨ての PostgreSQL・LocalStack を使う

## 2. テストの技法

テストのケースは、**ブラックボックステストで設計し、ホワイトボックステストで漏れを確かめる**（前回と同じ）。

```
① 仕様（機能要件・API 設計・データ構造）── ブラックボックスの技法 ──▶ ケースを設計して、先にテストを書く（Red）
② テストを通す最小限のコード（Green）→ 整理（Refactor）
③ カバレッジを測る ──▶ 通っていない分岐を見つける
④ 通っていない分岐が「仕様の漏れ」か「不要なコード」かを判断し、ケースを足す（または、コードを消す）
```

### 2.1 ブラックボックステスト（中身を見ず、仕様の入力と出力から考える）

| 技法 | 考え方 | このアプリで使う主な場面 |
|---|---|---|
| **同値分割** | 入力を「同じ扱いになるグループ（同値クラス）」に分け、各グループから代表を1つ選ぶ。有効なグループと無効なグループの両方を選ぶ | 入力チェック、記録方式（重量 × 回数・回数のみ・時間・距離）、単位（kg・lb、km・マイル）、目標の種類、閲覧する人と投稿者の関係 |
| **境界値分析** | グループの境目（最小・最大・その1つ外）を必ず確かめる。不具合は境目に集まる | 文字数・件数の上限、重量・体重の範囲と刻み、日付の区切り（日本時間の0時・月曜・月初・年初）、トークンの期限、達成率 100%、ページの区切り、カードの5種目・返信の3件 |
| **デシジョンテーブル** | 条件が複数あるとき、条件の組み合わせと結果を表にし、表の列ごとにケースを作る | 閲覧の制御、記録の作成・編集、自己ベスト更新の印、種目の要約、消費カロリー、通知を作るか、エラーの優先順位 |
| **状態遷移テスト** | 状態と、状態を変えるできごとを図にし、すべての遷移と「起きてはいけない遷移」を確かめる | フォローとリクエスト、鍵アカウントの切り替え、目標（進行中・期限切れ・達成済み）、確認用・再設定用・リフレッシュのトークン、ナイストレーニング・応援、画面のログイン状態 |
| **エラー推測** | 経験から「壊れやすい所」を予想してケースを足す | NFKC・絵文字・`\r\n`、`%` `_` `\`、日本時間と UTC のずれ、うるう年、lb の丸め、同時の操作、外部（S3・メール）の失敗、404 と 403 の取り違え（[5.10](#510-エラー推測壊れやすい所のチェックリスト)） |

### 2.2 ホワイトボックステスト（コードの中身を見て、通る道を考える）

| 網羅の基準 | 意味 | この計画での扱い |
|---|---|---|
| **命令網羅（C0）** | すべての行を1回以上通す | 最低限の目安 |
| **分岐網羅（C1）** | すべての分岐（if の真と偽、三項演算子、`switch` の各 case、`?.` など）の両方を1回以上通す | **主な目標**（[6章](#6-完了の基準)の基準） |
| **条件網羅** | `a && b` の a・b それぞれの真偽を通す | 条件が2つ以上ある if はケースを足す |
| パス網羅 | 分岐のすべての組み合わせを通す | 組み合わせが爆発するので目標にしない。重要な組み合わせはデシジョンテーブルで選ぶ |

- カバレッジは道具で測る：バックエンドは **JaCoCo**、フロントは **Vitest の coverage（v8）**
- カバレッジは「テストの量」ではなく「**漏れを見つける道具**」として使う。数字を上げるためだけのテスト（結果を確かめないテスト）は書かない
- **SQL の中の分岐は JaCoCo では測れない**。今回は自己ベスト・集計・消費カロリー・閲覧の制御・種目の要約を SQL で計算する（[データ構造の集計の SQL](./database.md#集計の-sql)）ので、これらは「デシジョンテーブルの列をすべてテストにした」ことを PR に書いて、網羅の代わりにする（[6章](#6-完了の基準)）

### 2.3 テストが本当に見張っているかの確認

- 新しく作るコード：テスト駆動の **Red**（先に失敗を確かめる）で確認する。PR に「最初に失敗したテストと、そのときの失敗の内容」を書く（CLAUDE.md）
- Red は「そのテストが今のコードで落ちる」ことしか示さない。境界の `<` と `<=` の取り違えなどを見逃していないかは、**実装の段階（[8章](#8-進め方)）の終わりごとに**、コードをわざと壊して（例：`<` を `<=` にする、閲覧の条件を1つ消す）テストが落ちることを確かめる（ミューテーションの確認）。PR に「壊した内容と落ちたテスト」を書く
  - 道具（PIT など）は使わず、前回と同じく手で行う。結合テスト（コンテナを使う）が多く、道具で全部の書き換えを試すと時間がかかりすぎるため。境界・閲覧の条件・計算の式に絞って壊す

## 3. テストの層

速くて安い単体テストを多く、遅い結合・E2E テストは大事な流れと横断の観点に絞る（テストのピラミッド）。

### 3.1 バックエンド

| 層 | 対象 | 道具 | DB・外部 | 確かめること | 主な技法 |
|---|---|---|---|---|---|
| **計算** | DB を使わない計算のクラス（単位の換算、種目の要約の最大のセットの選び方、自己ベストのセットの選び方、ハッシュタグの取り出し、達成率、期間の初日、カーソルの作り方と読み方、署名の時刻のそろえ方 など） | JUnit 5（Spring なし） | なし | 計算の結果・境界・丸め | 境界値・同値分割・デシジョンテーブル。**分岐網羅 100% を目指す** |
| **DB アクセス** | jOOQ で SQL を組み立てるクラス（以下「Repository」） | JUnit 5 + Testcontainers（`@JooqTest` 相当の小さな設定） | 本物の PostgreSQL（pg_bigm 入り。使い捨て） | SQL の結果：閲覧の制御・並び順・カーソル・絞り込み・集計・自己ベスト・消費カロリー・種目の要約・`ON CONFLICT`・CHECK 制約・CASCADE | デシジョンテーブル（閲覧の制御・自己ベスト・消費カロリー）・境界値（日付の区切り・カーソル）・エラー推測（`%` `_`・NFKC） |
| **Service** | 判断を行うクラス | JUnit 5 + Mockito（Spring なし） | Repository・S3・メール・時計は偽物 | 判断の分岐・エラーの種類・呼び出す Repository と引数・イベントを出すか | デシジョンテーブル・状態遷移・境界値。**分岐網羅（C1）の主な対象** |
| **Controller** | 76の API | `@WebMvcTest` + `@MockitoBean` | Service は偽物。認証の設定は本物 | URL・メソッド・ステータス・入力チェック（`@Valid`）・認証の要否・JSON の形・エラーの形・multipart の受け渡し | 同値分割（入力チェック）・デシジョンテーブル（認証 × 入力 × 結果） |
| **結合** | API から DB まで通し | `@SpringBootTest` + MockMvc + Testcontainers（`@Import(TestcontainersConfiguration.class)`） | 本物の PostgreSQL・LocalStack・Mailpit | 部品をつないだときの動き：トランザクション、保存の確定後の処理（Awaitility で待つ）、画像の保存と後片付け、メールの送信、N+1、同時の操作、**[4章](#4-このアプリで横断して確かめる観点)の横断の観点** | 状態遷移・エラー推測 |

- 前回は結合テストが多く（165件）、細かいケースをあとから単体テストへ寄せた。今回は最初から、**細かいケース（境界・組み合わせ）は単体テストか Repository のテスト**に、**結合テストはつないで初めて分かること**に分けて書く
- 計算を SQL で行うもの（自己ベスト・集計・消費カロリー・種目の要約）は、Service を偽物で囲んでも確かめられないので、Repository のテストで細かいケースを作る

### 3.2 フロントエンド・E2E

| 層 | 対象 | 道具 | 外部 | 確かめること | 主な技法 |
|---|---|---|---|---|---|
| **関数・通信** | 単位の換算と表示の丸め・ペースの表示・日付（週・月の区切り）・種目の要約の文言・Zod の入力チェック・`api/client.ts`（トークンの再発行とやり直し） | Vitest | `fetch` は偽物 | 計算・判定・エラーの変換 | 境界値・状態遷移・分岐網羅 |
| **UI 部品** | 投稿カード・セットの入力・種目の選択・単位つきの入力欄・ナイストレーニング／フォロー／応援のボタン・コメント（返信をさらに表示）・グラフ など | Vitest + Testing Library + jsdom | API は偽物 | 表示・ボタンの有効／無効・押したときの変化・入力エラーの表示・アクセシビリティ（ラベル） | 同値分割・状態遷移（押す前・通信中・成功・失敗） |
| **画面** | 23の画面（[画面仕様](./screens.md)） | Vitest + Testing Library | API は偽物（TanStack Query はテストごとに新しく作る） | 読み込み中・空・エラー・一覧の表示、続きの読み込み、画面の移動、入力中の内容の置き換えの確認 | 状態遷移・デシジョンテーブル |
| **E2E** | ユースケース（UC-01〜UC-58 の36件）と、シナリオでは足りない観点 | Playwright + `./gradlew bootTestRun` | すべて本物（使い捨てのコンテナ） | 画面とサーバーをつないだときの動き：Cookie でのログインの維持、画像の保存と署名付き URL での表示、メールのリンク（Mailpit から取り出す）、2人のユーザーでの閲覧の制御・通知、単位の切り替え、アクセシビリティ（axe）・スマートフォン幅・セキュリティ | ユースケース（状態遷移）・エラー推測 |

- テストのタイムゾーンは日本時間に固定する（[技術スタック](./tech-stack.md)）
- E2E は前回と同じ構成（`frontend/e2e/`、`bootTestRun` で使い捨てのコンテナにつなぐ、テストごとに違うユーザーを作る、下準備は API で行う）。Mailpit の API で届いたメールを読み、確認用・再設定用のリンクを開く

## 4. このアプリで横断して確かめる観点

機能ごとのテストとは別に、**すべての入口で同じ決まりが守られているか**を確かめる。前回はなかった観点で、漏れたときの影響が大きい（他人の非公開の記録・体重が見える、数値がずれる）。

### 4.1 閲覧の制御の漏れがないこと

[要件定義書 7章](./requirements.md)「閲覧の制御の漏れがないこと」と、[データ構造の閲覧の制御の条件](./database.md#閲覧の制御の条件)。

**① 条件そのもの（Repository のテスト）**：`WorkoutVisibility.visibleTo(me)` を、次の表の**すべての組み合わせ**で確かめる（○ ＝ 見られる、× ＝ 見られない）。

| 投稿の公開範囲 | 投稿者が鍵アカウント | 本人 | 承認済みのフォロワー | リクエスト中 | 投稿者からフォローされているだけ（逆向き） | 関係なし |
|---|---|---|---|---|---|---|
| 公開 | いいえ | ○ | ○ | （起きない※） | ○ | ○ |
| 公開 | はい | ○ | ○ | × | × | × |
| フォロワー限定 | いいえ | ○ | ○ | （起きない※） | × | × |
| フォロワー限定 | はい | ○ | ○ | × | × | × |
| 自分のみ | いいえ | ○ | × | （起きない※） | × | × |
| 自分のみ | はい | ○ | × | × | × | × |

- ※ 鍵アカウントでない人へのフォローはすぐ承認済みになり、鍵アカウントをやめるとリクエストはすべて承認される（F-53）ので、この組み合わせはデータとして起きない。鍵アカウントをやめたときに承認されることは、状態遷移（[5.8](#58-状態遷移フォローと鍵アカウント)）で確かめる
- 「逆向き」の列は、フォローの向きを取り違える不具合（`follower_id` と `followee_id` の逆）を見つけるために入れる
- 公開した目標（`goals.visibility`）の条件も、同じ表で確かめる。体重の目標は、DB の CHECK で `private` 以外にできないことも確かめる

**② すべての入口（結合テスト）**：見てはいけない投稿・目標に触れる API ごとに、「見てはいけない」「見てよい」の2つ以上のケースを作る。見てはいけない側は、表のうち一番間違えやすい「鍵アカウントの公開の投稿を、リクエスト中の人が見る」を使う。

| 入口 | 見てはいけないときの結果 |
|---|---|
| A-21 詳細・A-24 消費カロリー・A-60 コメント一覧・A-61 コメントの投稿・A-63／A-64 ナイストレーニング | 404 `WORKOUT_NOT_FOUND` |
| A-65 返信の続き・A-62 コメントの削除 | 404 `COMMENT_NOT_FOUND` |
| A-22 編集・A-23 削除 | 見てはいけないなら 404、見られる他人の記録なら 403（**404 と 403 の取り違え**を確かめる） |
| A-50・A-51 タイムライン・A-54 検索・A-81 プロフィールの記録・A-52／A-53 新しい投稿の件数 | 一覧に出ない・件数に入らない |
| A-120 通知一覧・A-121 未読数 | 見られなくなった投稿・コメントの通知が出ない・数えない（F-110） |
| 画像の URL | 見てはいけない投稿の画像の署名付き URL を作らない（応答のどこにも出ない） |
| A-84 公開した目標・A-116／A-117 応援 | 一覧に出ない・404 `GOAL_NOT_FOUND` |
| A-72・A-73 フォロー一覧 | 403 `PRIVATE_ACCOUNT` |

- **入口の書き忘れを防ぐ**：Spring に登録された API の一覧（`RequestMappingHandlerMapping`）から、パスに `{workoutId}`・`{commentId}`・`{goalId}` を含む API を取り出し、すべてが上の表のテストに入っていることを確かめるテストを置く。API を足して閲覧のテストを書き忘れると、このテストが落ちる
- 公開範囲を狭めた・フォローを解除した・鍵アカウントにしたあとに、見えなくなること（状態が変わったあと）も確かめる

### 4.2 健康に関わる情報を本人以外に出さないこと

[要件定義書 7章](./requirements.md)。体重・体脂肪率・消費カロリー・体重の目標・集計値。

- 結合テストで、**他人が呼ぶ API の応答の JSON（文字列そのもの）に、`Kcal`・`bodyWeight`・`bodyFat`・`currentKg`・`startKg` を含むキーがない**ことを確かめる。対象：A-21・A-50・A-51・A-54・A-60・A-80・A-81・A-84・A-120。値が `null` でもキーがあれば失敗にする（[API 設計の閲覧の制御](./api.md#閲覧の制御)の「null で入れることもしない」）
- A-24（消費カロリー）は、見てよい他人の記録でも 404
- 公開した目標（A-84）に、もとになった値（`progress.current`・`history`・`bodyWeight`）が入らない
- 集計（A-90〜A-97）・体重（A-100〜A-103）は、本人のデータしか返さない（他人のデータを作っておいて、結果に混ざらないことを確かめる）

### 4.3 単位の換算で値がずれないこと

[要件定義書 7章](./requirements.md)・[データ構造の単位の換算](./database.md#単位の換算と小数の桁)。値の種類が有限なので、**代表値ではなく全数で**確かめる（数万件でも1秒かからない）。

| 入力 | 全数 | 確かめること |
|---|---|---|
| 重量 lb | 0.5〜1100lb（0.5 刻み、2,200通り） | サーバーで kg（小数第3位、HALF_UP）にし、画面で lb に戻して 0.5 単位に丸めると、入力した値に戻る |
| 重量 kg | 0.25〜500kg（0.25 刻み、2,000通り） | 保存した値がそのまま表示される |
| 距離 マイル | 0.01〜310.68 マイル（0.01 刻み、31,068通り。500km まで） | km に戻して小数第2位に丸めると戻る |
| 体重 lb | 44.0〜661.0lb（0.2 刻み、3,086通り） | 同上（0.2 単位に丸める） |

- サーバー側（Java の `BigDecimal`）は計算のテストで、kg・km にする式を全数で確かめる。画面側（TypeScript）は関数のテストで、サーバーと同じ式で保存値を作ってから表示し直す全数テストをする
- サーバーと画面の式が同じであることは、**代表値の表（0.5lb → 0.227kg、135lb → 61.235kg、1100lb → 498.952kg など10個）を両方のテストに同じ形で持たせて**確かめる
- 刻みのチェック（kg は 0.25、lb は 0.5、マイルは 0.01）は、入力した単位で行われること（例：60.1kg は 400、132.5lb は保存できる）
- E2E（UC-58）で、lb・マイルに切り替えて入力 → 保存 → 表示し直し → kg に切り替え、の流れを確かめる

### 4.4 日付と日本時間

[要件定義書 7章](./requirements.md)・[データ構造の日付と日本時間](./database.md#日付と日本時間)。

- 時刻は `Clock` を差し替えて固定する（バックエンド）。画面は「今」を引数で渡す（前回と同じ）
- **バックエンドのテストは JVM と DB のセッションのタイムゾーンを UTC にして動かす**（Gradle の `test` に `-Duser.timezone=UTC`）。どこかで既定のタイムゾーンに頼っていると、日本時間の0時〜9時の境界のテストが落ちるので、書き漏れが見つかる
- 必ず確かめる境界

| 場面 | 境界の値（日本時間） |
|---|---|
| 「今日」と未来の日付（実施日・体重の日付・目標の期限） | 2026-11-14 23:59:59 と 2026-11-15 00:00:00（UTC では 11-14 14:59:59 と 15:00:00）に、実施日 11-15 を送る |
| 週の区切り（月曜始まり） | 日曜 23:59:59 と月曜 00:00:00。週間の集計・頻度と量の目標の期間 |
| 月をまたぐ週 | 2026-11-30（月）〜12-06（日）。月間の推移グラフは、その月の日だけを数える |
| 年をまたぐ週 | 2026-12-28（月）〜2027-01-03（日）。年間のランニングの集計 |
| うるう年 | 2028-02-29（月の日数・月間の頻度の目標 29日） |
| トークンの期限 | 確認用 24時間ちょうど・再設定用 30分ちょうど（期限ちょうどは使えない） |
| 署名付き URL | 10:59:59 と 11:00:00 で URL が変わり、同じ1時間の中では同じ URL になる |
| 期限切れ | 期限が昨日なら期限切れ、今日なら期限切れでない |

### 4.5 保存の確定後の処理

通知・目標の達成の判定・メールの送信・S3 の画像の削除は、保存の確定後に別のスレッドで動く（[技術スタック 3.6](./tech-stack.md)）。

| 確かめること | 方法 |
|---|---|
| 確定したあとに動く | 結合テストで API を呼び、Awaitility で通知・達成の行・メールができるのを待つ（`Thread.sleep` は使わない） |
| 取り消されたら動かない | 保存の途中で失敗させ（例：2枚目の画像の保存の失敗）、通知・メールができないことを、一定の時間待って確かめる（Awaitility の `during`） |
| 失敗しても、もとの操作は成功 | 通知を作る処理を失敗させても、API は 201・200 を返し、ログに残る（F-110） |
| 期間ごとに1回だけ | 同じ期間で2回 100% になる記録を保存しても、達成の行と通知は1件（`ON CONFLICT`） |

### 4.6 同時の操作

前回は「いいねの連打」「同時の再発行」だった。今回は件数の上限（[データ構造の件数の上限の守り方](./database.md#件数の上限の守り方)）が増えたので、**2つのスレッドから同時に呼ぶ結合テスト**（`CountDownLatch` で同時に始める）を作る。

| 操作 | 期待する結果 |
|---|---|
| 19件あるところに、テンプレート（上限20）を同時に2件作る | 1件だけ 201、もう1件は 409 `TEMPLATE_LIMIT_EXCEEDED`。合計20件 |
| 自分専用の種目（上限100）・達成済み以外の目標（上限10） | 同上 |
| 同じ投稿にナイストレーニング・同じ目標に応援を同時に2回 | 行は1件、通知は1件 |
| 同じ期間を 100% にする記録を同時に2件 | 達成の行と通知は1件 |
| 同じユーザー名で同時に新規登録 | 1件だけ 201、もう1件は 409 |
| 同じ日の体重を同時に2回記録 | 行は1件（上書き） |

### 4.7 N+1 がないこと

一覧の API で、件数によって SQL の数が増えないこと（[データ構造の N+1 問題を防ぐ](./database.md#n1-問題を防ぐ)）。jOOQ の `ExecuteListener` で SQL の数を数え、**1件のときと20件（1ページ分）のときで同じ**であることを確かめる。

- 対象：A-50・A-51・A-54・A-60・A-65・A-72・A-73・A-74・A-81・A-83・A-93・A-110・A-120
- 一覧の API を足したら、ここに足す（前回と同じ）

### 4.8 アカウントの安全

[要件定義書 7章](./requirements.md)「アカウントの安全」。

- パスワードのリセット（A-08）は、登録されている・いない・送信の上限を超えた・メールのサーバーが止まっている、のどれでも同じ 202 と同じ本文を返す
- 確認用・再設定用のトークンは、DB にハッシュだけが入り、元の値が入らない
- 1時間に5通を超えるメールは送らない（5通目は届き、6通目は届かない）。Mailpit で届いた数を数える
- パスワードの変更・リセットのあと、ほかの端末のリフレッシュトークンが使えなくなり、変更した端末はログインしたまま
- 位置情報（EXIF の GPS・XMP の位置）を含む画像を受け付けない（[API 設計 A-20](./api.md#a-20-記録の作成)）。位置情報のない EXIF（撮影日時だけ）は受け付ける

### 5.6 状態遷移：目標（F-100〜F-107）

**重量・体重の目標**（期限つき・期限なし）

```
            作成（達成率 < 100%。100% なら確定後の判定ですぐ達成済み）
                   │
                   ▼
   ┌──────────── 進行中 ──────────────┐
   │ 期限を過ぎる            記録・体重の保存で 100% │
   ▼                                   ▼
 期限切れ ── 期限を延ばす（編集）──▶ 進行中     達成済み（達成日を保存。通知）
                                             │ 記録を消して 100% を下回る → 達成済みのまま
```

| 今の状態 | できごと | 期待する結果 |
|---|---|---|
| 進行中 | 達成率 99.9…% になる記録 | 進行中のまま |
| 進行中 | 達成率ちょうど 100% になる記録・体重 | 達成済み（達成日 ＝ 今日、日本時間）。通知1件 |
| 進行中 | すでに達成している目標値に編集する | 確定後の判定で達成済み（A-113） |
| （なし）・進行中 | 体重の目標を、開始時の体重と同じ目標値で作成・編集する | 201・200。確定後の判定で達成済み。通知1件 |
| 進行中 | 体重の記録を消して、開始時の体重が目標値と同じになる | 達成率 100%（分母 0 で例外にならない）。次の体重の保存で達成済み |
| 進行中 | 期限の翌日になる | 期限切れ（列は変わらず、表示だけ） |
| 期限切れ | 期限を延ばす | 進行中 |
| 期限切れ | 目標を超える記録 | [9章](#9-設計で見つけた仕様の確認が必要な点)の確認事項 |
| 達成済み | 記録を消して 100% を下回る | 達成済みのまま（達成は取り消さない） |
| 達成済み | もう一度 100% になる記録 | 通知を作らない（更新件数 0） |
| どれでも | 削除 | 応援・通知も消える |

- 体重の目標は、減らす目標（75 → 70kg）と増やす目標（60 → 65kg）の両方で、同じ式で達成率が出ること。体重が反対の向きに動いたら 0%（0〜100% に丸める）。開始時の体重と目標値が同じ（維持する目標。70 → 70kg）ときは、今の体重が 70kg・69kg・71kg のどれでも 100%
- 開始時の体重：`started_on` の当日・前日の記録、`started_on` 以前の記録をすべて消したとき（`started_on` より後で一番近い記録を使う）

| その週に 100% になる記録 | 達成の行（`period_start` ＝ 月曜日）と通知1件。目標は一覧に残る |
| 同じ週にもう1件の記録 | 行も通知も増えない |
| 先週の日付の記録をあとから登録して、先週が 100% になる | 先週の達成の行ができる（達成日は今日） |
| 記録を消して 100% を下回る | 行は消えない |
| 目標値を変える | 過去の達成の行は消えない |
| 量の目標を種目で絞る・部位で絞る・絞らない | 対象の種目・部位のセットだけを合計する |

### 5.7 状態遷移：トークン

**リフレッシュトークン**は前回と同じ（有効 → 交換済み・ログアウト済み・期限切れ。交換済みを 10秒以内にもう一度使うと新しいトークン、10秒を過ぎると全無効化）。前回の遷移表をそのまま使い、「パスワードの変更・リセットで、変更した端末以外のトークンを無効にする」遷移を足す。

**確認用のトークン（メールアドレスの確認・変更）**

| 今の状態 | できごと | 期待する結果 |
|---|---|---|
| 有効（24時間以内） | リンクを開く | 確認済み（変更のときは新しいアドレスに変わる）。トークンは使えなくなる |
| 有効 | 確認メールを再送する | 前のトークンは使えなくなり、新しいトークンだけ使える（ユーザーごとに1行） |
| メールアドレスの変更の確認待ち | 確認メールを再送する（A-07） | 変更の確認用のリンクは使えなくなり、今のアドレスの確認用のリンクだけ使える |
| 期限ちょうど（24時間） | リンクを開く | 400 `INVALID_TOKEN` |
| 使用済み | もう一度開く | 400 `INVALID_TOKEN` |
| 変更の申請中 | 新しいアドレスが、その間にほかの人に登録された | リンクを開くと 409 `ALREADY_REGISTERED`（今のアドレスのまま） |
| 確認済み | 再送する | 409 `ALREADY_VERIFIED` |

**再設定用のトークン（パスワードのリセット）**：30分・1回だけ。期限ちょうど・使用済み・形の壊れたトークンで 400 `INVALID_TOKEN`。新しいパスワードが規則に合わない（400 `VALIDATION_FAILED`）ときは使用済みにせず、正しいパスワードでもう一度使える。再設定したら、すべてのリフレッシュトークンが無効になり、ログイン状態にはしない。

### 5.10 エラー推測：壊れやすい所のチェックリスト

前回のチェックリスト（文字・検索・時刻・同時の操作・外部の失敗・権限・一覧）に、このアプリで増えたものを足す。

- **文字の正規化**：ハッシュタグ・種目の名前の NFKC（`＃ＡＢＣ` と `#abc`、`ﾍﾞﾝﾁ` と `ベンチ`）、ハッシュタグの直前が文字のとき（`abc#tag` はハッシュタグか）、`#` だけ、絵文字のハッシュタグ
- **数値**：0回のセット、lb の丸め（0.5lb → 0.227kg）、`NUMERIC(6,3)` の上限、ペースの計算で距離が 0 や `null`、24:00:00 ちょうど、割り算の分母が 0（体重の目標・平均ペース）
- **日付**：[4.4](#44-日付と日本時間)の境界、月末（1月31日の翌月）、うるう年、11月に「毎月31日」の頻度の目標
- **削除の連鎖**：自分専用の種目をテンプレートから外す、記録・目標で使っている種目は消せない、返信元を消すと返信も消える、退会したユーザーへの返信は残り `@xxx` が出ない、退会で S3 の画像も消える
- **閲覧の取り違え**：404 と 403、フォローの向き、リクエスト中を承認済みとして扱う、他人の自分専用の種目の ID を送る、他人のテンプレート・目標・体重の ID・日付を送る
- **外部の失敗**：S3 に保存できない（保存した画像を消す）、メールのサーバーにつながらない（もとの操作は成功）、署名付き URL の期限が切れたあとの取り直し
- **画面**：入力中に単位の設定を変える（入力した値が別の単位にならない）、テンプレートの呼び出しで入力中の内容を置き換える確認、返信を投稿したあとに続きを読み込んで同じ返信が2回出ない、通信中の二重送信

## 6. 完了の基準

**機能を作る PR ごと**に、次を満たしたら完了とする。

| 対象 | 基準 |
|---|---|
| すべて | テストがすべて通る。たまに落ちるテストがない（時刻は固定、データはテストごとに用意、待つときは Awaitility） |
| 計算のクラス | 分岐網羅 100%。境界値の表（[5.1](#51-同値分割と境界値分析入力チェック)）のその機能の行をすべてテストにする |
| Repository | すべての SQL に正常のケースが1つ以上ある。SQL で計算するもの（[5.3](#53-デシジョンテーブル自己ベスト更新の印f-85)〜[5.5](#55-デシジョンテーブル消費カロリーf-86a-24)・閲覧の制御 [4.1](#41-閲覧の制御の漏れがないこと)）は、**デシジョンテーブルの列をすべて**テストにし、PR に「どの列をどのテストで確かめたか」を書く |
| Service | 分岐網羅 90% 以上。届かない分岐は、PR に理由を書く |
| Controller | すべての API で、基本のケース（下の表のうち当てはまるもの） |
| 横断の観点 | その PR で足した API が、[4章](#4-このアプリで横断して確かめる観点)の表（閲覧の制御・健康情報・N+1）に入っている |
| フロントの関数・通信 | 分岐網羅 90% 以上 |
| UI 部品・画面 | 読み込み中・空・エラー・成功の状態。分岐網羅は目安（80%）として測る |
| E2E | 実装の段階の終わりに、その段階のユースケースのシナリオ（[8章](#8-進め方)） |

Controller の基本のケース（前回と同じ）：

| ケース | 期待する結果 |
|---|---|
| 正しい入力・ログイン済み | 正しいステータス（200・201・202・204）と JSON の形 |
| ログインなし（ログインが必要な API） | 401 `UNAUTHENTICATED` |
| 入力チェックの違反 | 400 `VALIDATION_FAILED` と項目ごとのエラー（`errors`） |
| Service がエラーを返す（見つからない・権限なし・上限） | 404・403・409 と、そのエラーの `code` |
| 形の違うリクエスト（JSON が壊れている・ID が数字でない・カーソルが壊れている） | 400 `MALFORMED_REQUEST` / `VALIDATION_FAILED` |

- 基準を下回ったら CI を落とす（JaCoCo の `jacocoTestCoverageVerification`、Vitest の `coverage.thresholds`）。前回は途中から入れたが、今回は最初から基準を満たしながら作るので、最初から CI で守る

## 7. テストの書き方の決まり

前回の決まりを引き継ぐ。

- **名前**：日本語で「条件と結果」が分かるように書く（例：`前の記録と同じ重さなら自己ベスト更新の印を付けない()`、`test('135lb で入力した値は表示し直しても 135lb になる')`）
- **形**：準備 → 実行 → 確認 の3段。1つのテストでは1つのことを確かめる
- **境界値・デシジョンテーブルの並び**：同じ形で値だけ変えるケースは、`@ParameterizedTest`（JUnit）・`test.each`（Vitest）でまとめ、この計画書の表と同じ並びの「値の表」として読めるようにする
- **時刻**：`Clock.fixed`（バックエンド）・引数で「今」を渡す（フロント）。バックエンドのテストは JVM のタイムゾーンを UTC にして動かす（[4.4](#44-日付と日本時間)）
- **データ**：テストごとに必要なものだけ作る。ほかのテストのデータに頼らない。記録（種目・セット）のように形の大きいデータは、テスト用の組み立て役（`WorkoutFixture.of(user).weightReps("ベンチプレス", 60, 10, 3)` のような形）を用意して、テストの中では「そのケースで大事な値」だけを書く
- **偽物（モック）**：自分たちのコードの下の層だけを偽物にする（Service のテストでは Repository、Controller のテストでは Service）。DB の動きは偽物にせず、Repository のテストと結合テストで本物を使う
- **コンテナ**：`@SpringBootTest` のテストには `@Import(TestcontainersConfiguration.class)` を付ける（使い捨ての PostgreSQL（pg_bigm 入りの自作イメージ）・LocalStack・Mailpit。開発用の DB に書き込まない。H2 は使わない）。コンテナはテスト全体で1回だけ起動して使い回し、データはテストごとに消す
- **保存の確定後の処理**：Awaitility で待つ（`await().atMost(5, SECONDS).untilAsserted(...)`）。「起きないこと」は `during` で一定の時間確かめる。`Thread.sleep` は使わない
- **メール**：Mailpit の API で、宛先・件名・本文のリンクを確かめる。テストの最初に Mailpit の中身を空にする
- **SQL の数**：jOOQ の `ExecuteListener` で数える部品を、テスト用に1つ用意する（[4.7](#47-n1-がないこと)）
- **実行の確かめ方**：キャッシュではなく実際に実行した結果で確かめる（Gradle は `--tests` で対象を絞るか、`--rerun-tasks` を付ける）
- **置き場所**：バックエンドは対象と同じパッケージ、フロントは対象のファイルの隣（`〇〇.test.ts(x)`）
- **フロントの実行環境・偽物の時計・状態を持つモジュール**：前回と同じ（`// @vitest-environment jsdom`、必要なものだけ偽物の時計にする、`vi.resetModules()`）。TanStack Query の `QueryClient` はテストごとに新しく作り、再試行を切る（`retry: false`）

## 8. 進め方

[要件定義書 11章](./requirements.md) の実装の順番に合わせて、段階ごとに進める。テストは機能と同じ PR で書く（テスト駆動）。各段階の終わりに、ミューテーションの確認（[2.3](#23-テストが本当に見張っているかの確認)）と、その段階のユースケースの E2E を行う。

| 段階 | 内容 | E2E にするユースケースの例 |
|---|---|---|
| 0 | テストの土台：CI（`.github/workflows/ci.yml`）、Testcontainers の設定（pg_bigm 入りのイメージ・LocalStack・Mailpit）、JaCoCo・Vitest の coverage と基準、SQL の数を数える部品、テスト用の組み立て役、E2E の起動（`bootTestRun`） | — |
| 1 | 前回と同じ部分：認証・記録（種目・セット・画像）・ナイストレーニング・コメントと返信・フォロー・タイムライン | 登録・ログイン、記録を作る（画像つき）、ナイストレーニング・コメント・返信、フォローしてタイムラインに出る |
| 2 | 記録と集計：自己ベスト・週間と月間・カレンダー・ランニング・種目ごとの推移・体重 | 記録して集計・自己ベストを見る、ランニングの記録、体重を記録する |
| 3 | 目標：作成・達成の判定・公開・応援 | 目標を作り、記録で達成して通知が届く、他人の目標を応援する |
| 4 | 通知・鍵アカウント・検索・テンプレート | 鍵アカウントのリクエストと承認、投稿・ハッシュタグ・種目での検索、テンプレートの保存と呼び出し |
| 5 | アカウント管理・単位・消費カロリー | メールアドレスの確認・変更、パスワードのリセット、退会、単位の切り替え（[4.3](#43-単位の換算で値がずれないこと)） |
| 6 | シナリオでは足りない観点：アクセシビリティ（axe）・スマートフォン幅・レイアウトのずれ・セキュリティ（XSS・Cookie の属性・トークンの置き場所） | — |

- 段階 6 の観点は前回の 9.11 と同じ。前回見つかった色のコントラストの問題を繰り返さないよう、画面を作る段階から axe のチェックを E2E に入れておく
- 各 PR の本文には、「使った技法と作ったケース」「Red → Green の記録」「カバレッジ」を書く。段階の終わりの PR には、「壊した内容と落ちたテスト」も書く

## 9. 設計で見つけた、仕様の確認が必要な点

この計画書のケースを洗い出す中で、仕様の文書に書かれていない動きが見つかった。実装の前に決めて、機能要件・API 設計に反映する。

| 項目 | 内容 | 案 |
|---|---|---|
| 期限切れの目標を超える記録 | 期限を過ぎてから目標値に届いたときに、達成にするか決まっていない | 達成にしない（期限切れのまま）。期限を延ばす編集をすれば、確定後の判定で達成になる |

| 月の日数を超える頻度の目標 | 「毎月31日」の目標は、30日以下の月には達成できない | そのままにする（目標値の上限は 31 のまま）。画面の案内は付けない |

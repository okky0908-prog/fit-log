# 技術スタック

[要件定義書](./requirements.md) の詳細ドキュメント。FIT LOG の技術スタックと、それを選んだ理由・比べた候補をまとめる。

## 1. 選び方

- 「前回の SNS アプリと同じ」を前提にせず、**このアプリの要件と性能にとって最善のもの**を比べて選ぶ（2026-11-13 に比較）
- そのうえで、学習の目的（[要件定義書 2章](./requirements.md)：一段複雑なデータと処理）に合うものを優先する

### 1.1 性能の差がどこで出るか

このアプリの規模（1ユーザーあたり1年で約300投稿・約1万セット）では、1回の API の応答時間は、ほとんどが **DB への問い合わせと通信**で決まる。言語やフレームワークそのものの処理にかかる時間はミリ秒未満で、使っていて感じるほどの差にならない。性能に差が出るのは次の3つなので、**これらを正しく作りやすいかどうか**を選ぶ基準にした。

1. **SQL を何回投げるか、インデックスが効いているか**（DB へのアクセスの書き方で決まる）
2. **画像の大きさとキャッシュ**（画面の表示の速さはこれが一番大きい）
3. **フロントで最初に読み込む JS の量**（グラフのライブラリの大きさで決まる）

## 2. バージョンの決め方

- **前回の SNS アプリ（`SNSアプリ`）と同じ技術は、同じバージョンから始める**。前回動作確認済みの組み合わせなので、環境構築でつまずきにくく、前回のコードや設定をそのまま参考にできる
  - バージョンの出どころ: [`SNSアプリ/docs/tech-stack.md`](../../SNSアプリ/docs/tech-stack.md)（2026-11-13 確認）
- **今回新しく使う技術**は、導入するときに、公開から2週間以上たった版のうち最新の安定版を使い、`package.json` / `build.gradle.kts` で固定したうえで、この表の「未定」を書き換える
- **Spring Boot が管理しているライブラリ**は、バージョンを自分で書かず、Spring Boot が決めるバージョンに任せる（脆弱性があって Spring Boot の新しい版がまだ出ていないときだけ、`build.gradle.kts` で直った版を指定する）
- 脆弱性が見つかったときと Dependabot の更新は、前回と同じ版にこだわらず、直った版に上げる
- 表の「前回」列: ○ は前回と同じ技術、新規 は今回初めて使うもの、変更 は前回の技術から置き換えたもの

## 3. 比べた内容と選んだ理由

### 3.1 バックエンドの言語・フレームワーク → Java 25 + Spring Boot 4.1

| 候補 | 良い点 | 気になる点 |
|---|---|---|
| **Java 25 + Spring Boot 4.1**（採用） | 認証（JWT）・S3・Testcontainers・Terraform・CI を前回から使い回せる。スクールの教材とも合う | 記述量が多い。前回は Jackson 2 と 3 が混ざり、版の管理に手間がかかった |
| Kotlin + Spring Boot | null 安全と data class で、入れ子の DTO を短く書ける | 言語を新しく覚える必要があり、学習の重点がデータと処理からずれる |
| TypeScript（Hono / NestJS） | フロントと API の型を共有できる | 認証・テスト・インフラを作り直しになる |
| Go / Rails / FastAPI | それぞれ強みはある | このアプリの要件に対して、乗り換える理由が弱い |

実行環境ごとの性能の目安（実際の値は、パフォーマンステストで測って確かめる）：

| | Spring Boot（JVM） | Spring Boot（GraalVM ネイティブ） | Go | Node.js |
|---|---|---|---|---|
| 起動時間 | 数秒 | 0.1秒前後 | ミリ秒単位 | 1秒未満 |
| 待機中のメモリ | 300〜500MB | 100MB前後 | 数十MB | 100MB前後 |
| 1リクエストの処理 | DB 待ちが大半のため、どれも差は小さい | ← | ← | ← |

- Fargate ではタスクをずっと動かしておくので、起動時間の差は効かない。差が出るのはタスクのメモリ代（月に数ドル〜十数ドル）だけで、言語を変える理由にはならない
- GraalVM のネイティブイメージは、ビルドが遅く、使うライブラリの対応も確かめる必要があるため使わない
- **仮想スレッド**（`spring.threads.virtual.enabled=true`）を使う。DB や S3 を待つ間にスレッドを手放すので、同時にさばけるリクエストの数が増える。Java 24 以降は `synchronized` の中でもスレッドが固定されにくくなった（JEP 491）。同時に使える DB の接続の数は、接続プール（HikariCP）の大きさで決まることに注意する

### 3.2 DB → PostgreSQL 17 + pg_bigm

| 要件 | PostgreSQL | MySQL 8 |
|---|---|---|
| 週（月曜始まり）・月・年で区切る | `date_trunc('week', …)` がそのまま月曜始まり | 工夫が要る |
| 記録のない日も0として並べる（グラフ・カレンダー） | `generate_series` で日付を作れる | 再帰 CTE などで作る |
| 部位別の集計を1回の SQL で | `FILTER` 句 | `CASE` で書く |
| 日本語の部分一致検索に索引を使う | **pg_bigm**（2文字単位の索引。RDS でも使える） | ngram の全文検索（使えるが、日本語の短い語の扱いに癖がある） |

- 標準の全文検索（`tsvector`）は日本語を単語に区切れない。**pg_trgm**（3文字単位）は、「胸筋」のような2文字の語で索引が効かないので使わない
- 公式の Docker イメージ `postgres:17` には pg_bigm が入っていないため、**pg_bigm を入れたイメージを自分で作る**（`db/Dockerfile`）。docker-compose と Testcontainers の両方でこのイメージを使う
- RDS for PostgreSQL 17 で pg_bigm が使えること・その版を、導入するときに確かめる

### 3.3 DB へのアクセス → jOOQ（MyBatis から変更）

タイムラインで20件の投稿（1件あたり5種目×4セット、画像4枚）を読み込む場合：

| 書き方 | SQL の回数 | DB から返る行数 | 評価 |
|---|---|---|---|
| JPA で、関連データを使うときに読み込む設定のまま | 1 + 20 + 100 … | 少ない | N+1 の問題で遅い |
| MyBatis で、1回の JOIN と `<collection>` で組み立てる | 1 | 20×5×4×4 = 1,600行（同じ値が何度も返る） | 画像と種目を同時に JOIN すると、行数が掛け算で増える |
| MyBatis で、`IN` を使って3回に分けて読み込む | 3 | 約500行 | 速い。書く量はやや多い |
| **jOOQ の `multiset`**（採用） | 1 | 20行（入れ子を PostgreSQL が JSON にまとめて返す） | 速い。型安全 |

- MyBatis でも速くはできる。jOOQ を選んだのは、このアプリに**集計の SQL が多い**ため（週・月・年の集計、ランニングのペースとベスト記録、推定 1RM の推移、消費カロリー、閲覧の判定）。jOOQ なら、ウィンドウ関数や `FILTER` 句も Java の型つきで書け、列名や型の間違いがコンパイル時に見つかる
- 閲覧の判定（公開範囲・鍵アカウント）を、どの一覧でも使い回せる**1つの条件（`Condition`）**として書ける。判定の書き漏れを防ぎやすい
- 値は jOOQ がバインド変数として渡すので、SQL インジェクションを防げる。文字列で SQL をつなげる書き方（`DSL.field(String)` に外から来た値を入れるなど）はしない
- **コードの自動生成**：Gradle のビルドの中で、Testcontainers で PostgreSQL（pg_bigm 入りのイメージ）を立ち上げ、Flyway でテーブルを作ってから jOOQ のコードを作る。生成したコードはリポジトリに入れない（CI でも Docker を使えるため）

### 3.4 フロントエンドのフレームワーク → React + Vite の SPA

| 候補 | 評価 |
|---|---|
| **React + Vite の SPA**（採用） | 全画面がログイン必須で SEO が要らないので、SPA で十分。CloudFront + S3 の配信を前回から使い回せる |
| Next.js | サーバー側の描画（SSR）を活かせる場面がなく、動かすサーバーが1つ増えるだけ |
| Vue / Svelte | このアプリの規模では、使っていて分かるほどの性能の差はなく、乗り換える理由が弱い |

### 3.5 フロントで新しく使うもの

| 項目 | 比べた候補 | 採用と理由 |
|---|---|---|
| サーバーのデータの管理 | 自前の fetch + useState（前回）／**TanStack Query**／SWR | **TanStack Query**。記録を投稿したら、タイムライン・集計・目標の達成率・自己ベストを一度に取り直す必要があり、自前では漏れやすい。一度取ったデータを覚えておくので、画面を戻ったときに通信をやり直さない。スクロールでの続きの読み込み（`useInfiniteQuery`）と、通知の未読数の定期的な取り直し（`refetchInterval`）にも使う |
| 入れ子のフォーム | useReducer（自前）／**React Hook Form + Zod**／TanStack Form | **React Hook Form + Zod**。種目（20件まで）とセット（20件まで）の追加・並べ替えは `useFieldArray`、記録方式ごとの入力の検証は Zod の `discriminatedUnion` がちょうど合う。テンプレートや前回の記録の呼び出しは `reset()` で値を入れるだけで済む。入力の検証はサーバーでも必ず行う（フロントの検証は使いやすさのため） |
| セットの並べ替え | dnd-kit／**上下ボタン** | **上下ボタン**（ライブラリなし）。スマホでのドラッグは押し間違いが起きやすく、キーボードでも操作しやすい |
| グラフ | **Recharts**／Chart.js／ECharts／Nivo／visx | **Recharts**。React の部品として書けて、SVG なので読み上げにも対応させやすい。描く点の数は多くても数百（1年分の推移）で、SVG で十分。数千点を超えるなら Canvas の Chart.js が有利。ECharts は容量が大きく、visx は自分で組み立てる量が多い。**グラフを使う画面だけを後から読み込む**（`React.lazy`）ようにして、タイムラインを最初に開く速さに影響させない。容量は `vite build` のあとに実測する |
| カレンダー | ライブラリ／**自作（CSS Grid）** | **自作**。印を付けて押せるだけなので、ライブラリは要らない |
| 日付の計算 | **date-fns**／Day.js／Temporal | **date-fns**（`startOfWeek(…, { weekStartsOn: 1 })` など、使う関数だけを読み込める）。Temporal は、Safari を含む主なブラウザが対応したら検討する |
| 画像の縮小 | **ブラウザの Canvas**／サーバー側（Lambda など） | **ブラウザの Canvas**（ライブラリなし）。`createImageBitmap` で読み込み、長い辺を決めた大きさに縮めてから送る。スマホの写真は1枚 3〜5MB あり、縮めるかどうかで表示の速さが何倍も変わる。WebP に書き出せないブラウザ（`toBlob` の結果が WebP にならないとき）では JPEG にする |
| 単位の換算 | ライブラリ／**自作** | **自作**（kg⇔lb・km⇔マイルの換算と、ペースの表示だけ）。換算の式をテストで確かめる |

### 3.6 保存のあとに行う処理（通知・目標の達成・メール・画像の削除）

| 候補 | 評価 |
|---|---|
| 保存と同じ処理の中で行う | 通知の作成やメールの送信が失敗すると、もとの操作まで失敗する。応答も遅くなる |
| **Spring のイベント**（`@TransactionalEventListener` で保存の確定後に、`@Async` で別のスレッドで実行）（採用） | 追加の AWS のサービスが要らない。もとの操作の応答を待たせない |
| SQS（メッセージのキュー） | 失敗したときに確実にやり直せるが、この規模では手間に見合わない |

- イベントの処理が失敗しても、もとの操作は成功のままにし、失敗はログに残す（通知が1件届かない程度で済むため）
- テストでは、別のスレッドの処理が終わるのを Awaitility で待って確かめる

### 3.7 通知を届ける仕組み → ポーリング

| 候補 | 評価 |
|---|---|
| **ポーリング**（一定の間隔で未読数を問い合わせる）（採用） | 作りが単純。1分ごとなら、この規模では負荷は小さい |
| SSE / WebSocket | すぐに届くが、接続をつなぎっぱなしにする。Fargate のタスクが2つ以上になると、タスクの間でメッセージを受け渡す仕組み（Redis か、PostgreSQL の LISTEN/NOTIFY）が要る。ALB の接続のタイムアウトの設定も要る |

### 3.8 メール → Amazon SES（手元の開発・テストは Mailpit）

| 候補 | 評価 |
|---|---|
| **Amazon SES**（採用） | AWS の中で完結し、ECS のタスクの IAM ロールで送れる（鍵を保存しなくて済む）。安い |
| SendGrid / Resend | API キーを SSM に保存して管理する必要がある |

- 送信はアプリの中の小さな interface にまとめ、**本番は AWS SDK v2 の SES クライアント**、**手元の開発とテストは SMTP で Mailpit** に送る。Mailpit は送ったメールを画面と API で確かめられる
- SES は最初「サンドボックス」（確認済みのアドレスにしか送れない）の状態なので、ほかの人に送るには解除の申請が要る
- 送信元として独自ドメインを確認して、SPF・DKIM を設定すると、メールが迷惑メールに入りにくくなる（独自ドメインを取得するかは [要件定義書 10章](./requirements.md) の未決定事項）

### 3.9 画像の閲覧制御 → S3 の署名付き URL

要件定義書 7章で「画像の URL でも公開範囲を判定する」としているので、誰でも見られる CloudFront の URL（前回）は使えない。

| 候補 | 評価 |
|---|---|
| **S3 の署名付き URL（期限つき）を、閲覧を許可したときだけ API が発行する**（採用） | 作りが単純で、期限が切れれば見られなくなる。署名の計算はサーバーの中だけで済む（通信しない）ので、一覧で80個発行しても速い |
| CloudFront の署名付き URL・Cookie | 途中のキャッシュが効くが、署名用の鍵の管理と Terraform の設定が増える |
| API を通して画像を返す | 確実だが、API サーバーの負荷が高い |

- 有効期限を「1時間ごとの区切り」にそろえ、その間は同じ URL を返す。URL が毎回変わるとブラウザのキャッシュが効かなくなるため
- 投稿の一覧・詳細の API で閲覧を判定したあとに URL を発行するので、判定の入口を1か所にまとめられる

### 3.10 認証・インフラ → 前回の仕組みを使い回す

- **認証**：JWT（アクセストークン＋リフレッシュトークン）。Cognito なども候補だが、今回の学習の目的から外れる
- **インフラ**：ECS Fargate + ALB + RDS を Terraform で構築する。Lambda（SnapStart）＋ Aurora Serverless v2 にすれば待機中の費用は下げられるが、作り直す手間に見合わない。費用は、使わないときは止めることと AWS Budgets で抑える
- 定期的な掃除（期限切れのトークン・古い通知の削除）は Spring の `@Scheduled` で行う。タスクが2つ以上あっても、削除は何度実行しても結果が同じなので問題にならない

## 6. データベース・永続化

| 項目 | 技術・バージョン | 前回 | 理由・補足 |

| DB | PostgreSQL 17（手元・テストは pg_bigm 入りの自作イメージ、AWS は RDS for PostgreSQL 17） | ○ | 3.2 |
| 日本語の検索 | pg_bigm（未定） | 新規 | 3.2 |

## 10. 今回は採用しなかったものと、考え直すきっかけ

| 技術 | 考え直すきっかけ |
|---|---|
| SSE / WebSocket（通知をすぐに届ける） | 「すぐに届く」ことが必要になったとき（[要件定義書 4.2](./requirements.md)） |
| SQS | 通知・メールの取りこぼしが許されなくなったとき、または処理が重くなってきたとき |
| OpenSearch | 投稿が大幅に増えて、pg_bigm の検索が遅くなったとき（月に数十ドル以上かかる） |
| CloudFront の署名付き URL・Cookie | 画像の転送量が増えて、途中のキャッシュが必要になったとき |
| GraalVM のネイティブイメージ | タスクのメモリ代を下げたいとき、または起動の速さが必要な構成（Lambda など）に移すとき |
| Kotlin | Java の記述量が開発の負担になったとき（同じ Spring Boot のまま移せる） |

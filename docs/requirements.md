# 要件定義書：FIT LOG（SNS風 筋トレ・運動記録アプリ）

## 1. 概要

筋トレ・運動の記録を投稿し、仲間と励まし合える SNS 風の Web アプリケーション。
1回のトレーニング（種目・セットごとの重量と回数、有酸素運動の時間と距離、写真）を1件の投稿として記録し、仲間からの「ナイストレーニング」（いいね）やコメント（アドバイス・応援）を受け取れる。記録は週間・月間・年間で自動集計され（ランニングの距離・ペース・ベスト記録、消費カロリーの目安を含む）、自分で立てた目標の達成度を確認できる。

スクールの上級課題として開発する。

## 2. 背景・目的

- 本プロジェクトはスクールの上級課題であり、特定の業務課題やビジネス上の目的があるわけではない
- 主目的は学習：前回の X 風 SNS アプリ（`SNSアプリ`）で身につけた「認証・投稿・画像（S3）・いいね・コメント・フォロー」を土台に、**一段複雑なデータと処理**を扱う
  - **構造化された記録**：投稿の中に「種目 → セット」という親子関係のデータを持つ（前回の投稿はテキストと画像だけだった）
  - **集計**：週・月・年ごとのトレーニング日数・総挙上量（重量 × 回数の合計）・運動時間・距離・ランニングのペースとベスト記録・消費カロリー・部位別の割合を SQL で集計し、グラフで表示する
  - **目標と達成率**：4種類の目標（頻度・量・重量・体重）を、記録から自動で達成率を計算して表示する
  - **公開範囲による閲覧の制御**：投稿ごとに「公開／フォロワー限定／自分のみ」を選べ、鍵アカウント（フォローの承認制）と合わせて、見てよい人だけに見せる（前回は全投稿が全員に見えた）
  - **保存のあとに行う処理**：通知の作成・目標の達成の判定・メールの送信を、投稿などの保存が確定したあとに行う
  - **日本語の検索**：投稿のひとことの部分一致検索とハッシュタグ
- 副次的な狙いとして、開発者自身が実際にトレーニング記録に使えるものを作る
- 技術は「前回と同じ」を前提にせず、このアプリにとって最善のものを比べて選ぶ（[技術スタック](./tech-stack.md)）

### 2.1 アプリの方針（ほかの SNS・記録アプリとの違い）

- **数字を競わせない**：フォロワー数ランキング・他人との記録の比較ランキングは置かない。比べる相手は「過去の自分」とする（自己ベストの更新、先週・先月との比較）
- **励まし合いに集中する**：いいねは「ナイストレーニング」という名前にし、投稿への反応を前向きなものにする。目標は仲間に公開して応援してもらえる
- **記録は非公開でも残せる**：人に見せたくない日の記録や体重は「自分のみ」にでき、非公開の記録も自分の集計・目標には含める

## 3. 想定利用者

- 筋トレ・運動を習慣にしたい受講生・個人（複数ユーザー）
- 利用にはアカウント登録・ログインが必要。未ログインで使えるのは、ログイン・新規登録・パスワードのリセット・メールアドレスの確認の画面のみ
- 管理者（ユーザーの凍結、投稿の強制削除、種目マスタの管理画面など）は想定しない。最初から用意する種目はマイグレーションで登録する

## 4. スコープ

### 4.1 今回実装する範囲

| 分類 | 内容 |
|---|---|
| 認証 | 新規登録（ユーザー名・メールアドレス・パスワード）・ログイン・ログアウト（アクセストークン＋リフレッシュトークン） |
| アカウント管理 | メールアドレスの確認、パスワードの変更・リセット（メールで再設定）、退会 |
| トレーニング記録（投稿） | 作成・編集・削除・詳細表示。実施日・ひとこと（本文）・トレーニング時間・種目とセット・画像（4枚まで）・公開範囲 |
| テンプレート・複製 | よく行うメニュー（種目とセット）を保存して呼び出す。前回の記録を複製して新しい記録を作る |
| 種目 | 最初から用意された種目（部位・記録方式・METs つき）から選ぶ。見つからない種目は自分専用の種目として追加できる |
| 自己ベスト | 種目ごとの最大重量を記録から求め、更新した投稿に「自己ベスト更新」の印を付ける |
| 種目ごとの推移 | 種目ごとの最大重量・推定 1RM（最大挙上重量）・回数の推移グラフ |
| タイムライン | フォロー中タイムライン・全体タイムライン（どちらも見てよい投稿だけ） |
| 投稿の検索 | ひとことの部分一致・ハッシュタグ・種目での絞り込み（見てよい投稿だけ） |
| ナイストレーニング（いいね） | 付ける・取り消す、数の表示 |
| コメント | 投稿・一覧・削除、数の表示、コメントへの返信（1段） |
| フォロー（仲間） | フォロー・フォロー解除、フォロー中・フォロワー一覧、数の表示 |
| 鍵アカウント | フォローの承認制。フォローのリクエストの承認・拒否 |
| 通知 | ナイストレーニング・コメント・返信・フォロー・フォローのリクエストと承認・目標の達成。未読数の表示、既読にする |
| プロフィール | 表示・編集（表示名・自己紹介・アイコン画像）、そのユーザーの投稿一覧と公開された目標 |
| ユーザー検索 | `@ユーザー名`・表示名の部分一致 |
| 記録の集計 | 週間（月曜〜日曜）・月間の集計とグラフ、記録した日が分かるカレンダー |
| ランニングの集計 | 走行距離・平均ペース（1km あたりの時間）・ベスト記録（最速ペース・最長距離）を週間・月間・年間で集計 |
| 消費カロリー | METs と体重から消費カロリーの目安を自動計算し、投稿と集計に表示する（本人だけ） |
| 体重の記録 | 日付・体重・体脂肪率（任意）の記録と推移グラフ。本人だけが見られる |
| 目標設定 | 4種類の目標の作成・編集・削除・達成率の表示、達成した目標の一覧、目標の公開と応援 |
| 単位の切り替え | 重量（kg／lb）・距離（km／マイル）の表示と入力の切り替え |

### 4.2 将来的に追加したい範囲（今回は対象外）

- 通知をすぐに届ける仕組み（SSE・WebSocket）。今回は一定の間隔で未読数を問い合わせる（[技術スタック](./tech-stack.md)）
- メール・プッシュ通知、通知の種類ごとのオン・オフ
- 何段でも続く返信（今回は1段まで）
- ランニング以外の有酸素運動（バイク・水泳など）のペースとベスト記録の集計

### 4.3 明確に対象外とするもの

- ランキング・他人との記録の比較（2.1 の方針により、今後も追加しない）
- リポスト（シェア）・インプレッション数の表示
- ダイレクトメッセージ
- ウェアラブル端末・ヘルスケアアプリとの連携
- AI による自動アドバイス
- 管理者機能

## 5. 機能要件（概要）

詳細（機能一覧・処理の流れ・エラー時の動き・受け入れ条件）は、次の段階で [機能要件](./features.md) にまとめる。ここでは各機能の範囲と主な決まりごとを定める。

### 5.1 トレーニング記録（投稿）

1件の投稿 ＝ 1回のトレーニング とする。

| 項目 | 必須 | 内容 |
|---|---|---|
| 実施日 | ○ | トレーニングをした日。初期値は今日。過去の日付も選べる（記録し忘れた日の分をあとから登録できる）。未来の日付は選べない |
| ひとこと | － | 本文。280文字まで（感想・調子など）。`#` から始まる語はハッシュタグとして扱う（5.10） |
| トレーニング時間 | － | その日のトレーニング全体にかかった時間（分）。消費カロリーの計算に使う（5.13） |
| 種目 | ○ | 1件以上、20件まで。並び順を持つ |
| セット | ○ | 種目ごとに1件以上、20件まで。並び順を持つ。入力する値は種目の記録方式（下表）で決まる |
| 画像 | － | 4枚まで（JPEG・PNG・WebP）。アップロードの前にブラウザで縮小する |
| 公開範囲 | ○ | 公開／フォロワー限定／自分のみ。初期値は「公開」 |

種目の記録方式とセットの入力項目：

| 記録方式 | 例 | セットの入力項目 | 集計に使う値 |
|---|---|---|---|
| 重量 × 回数 | ベンチプレス、スクワット | 重量・回数 | 総挙上量（重量 × 回数）、最大重量（自己ベスト）、推定 1RM |
| 回数のみ | 腕立て伏せ、懸垂 | 回数 | 合計回数 |
| 時間・距離 | ランニング、バイク | 時間（時:分:秒）・距離（任意） | 運動時間・距離・ペース（ランニング） |

- 重量・距離は、DB には常に **kg・km で小数第3位まで**保存する。入力と表示は、ユーザーが選んだ単位（5.14）で行う
  - 入力の刻み：kg は 0.25、lb は 0.5。距離は km・マイルとも 0.01
  - 例：135lb で入力すると 61.235kg として保存し、表示し直すと 135lb に戻る
- 時間は**秒**で保存する（ランニングのペースを秒単位で出すため）
- 種目には部位（胸・背中・脚・肩・腕・腹・全身・有酸素）を1つ持たせ、部位別の集計に使う
- 種目には **METs**（運動の強さ）を持たせ、消費カロリーの計算に使う。有酸素の種目のうち、ランニング・ジョギング・トレッドミルなどは「ランニング」として分類し、ランニングの集計（5.5.1）に使う
- 種目は、最初から用意された種目（約50種類）から選ぶ。見つからないときは、名前・部位・記録方式を決めて**自分専用の種目**を追加できる（ほかのユーザーには、投稿に表示される名前としてだけ見える）。自分専用の種目の METs は、部位と記録方式から決めた標準の値を使う
- 編集・削除できるのは投稿者本人だけ。編集すると集計・自己ベスト・消費カロリーも作り直した値になる

### 5.2 公開範囲と閲覧の制御

| 公開範囲 | 見られる人 | ナイストレーニング・コメントできる人 |
|---|---|---|
| 公開 | ログインしている全員（鍵アカウントの場合は、フォロワー限定と同じ） | 見られる人全員 |
| フォロワー限定 | 投稿者本人と、投稿者をフォローしている人（鍵アカウントの場合は、承認されたフォロワーだけ） | 見られる人全員 |
| 自分のみ | 投稿者本人だけ | 本人だけ（自分の記録へのメモとして） |

- 一覧（タイムライン・プロフィール・検索）でも、詳細・ナイストレーニング・コメントの API でも、画像の URL の発行でも、同じ規則で判定する。見てはいけない投稿は「存在しない」として扱う（404）
- 公開範囲はあとから変更できる。狭めた場合、すでに付いたナイストレーニング・コメントは消さないが、見られなくなった人には投稿ごと見えなくなる
- フォローを解除すると、その人のフォロワー限定の投稿は見えなくなる
- 集計・目標・自己ベストには、公開範囲に関係なく本人の全投稿を含める

### 5.3 ナイストレーニング・コメント・フォロー

前回の SNS アプリの決まりに、返信と鍵アカウントを加える。

- ナイストレーニングは1人1投稿につき1回まで（DB の一意制約で保証）。自分の投稿にも付けられる
- コメントは140文字まで。削除できるのはコメントを書いた本人と、投稿者本人
- **返信**：コメントに返信できる。返信は1段までとし、返信への返信は同じ段に並べる（返信先のユーザー名を表示する）。返信元のコメントを削除すると、その返信も消える
- フォローは自分自身にはできない。同じ人を重ねてフォローできない（一意制約）
- **鍵アカウント**：プロフィールの設定で切り替える
  - 鍵アカウントをフォローすると「リクエスト中」になり、相手が承認するとフォロワーになる。相手が拒否するとリクエストは消える（拒否したことは相手に通知しない）
  - リクエスト中の人は、フォロワー限定の投稿を見られない
  - 鍵アカウントをやめると、承認待ちのリクエストはすべて承認されたものとして扱う

### 5.4 自己ベスト・種目ごとの推移

- 「重量 × 回数」の種目について、1回以上挙げたセットの最大重量を、種目ごとの自己ベストとする
- 投稿したセットがそれまでの自己ベストを超えたとき、その投稿の種目に「自己ベスト更新」の印を付ける（初めて記録した種目には付けない）
- 投稿の編集・削除で記録が変わった場合も、自己ベストは記録から計算し直す（値を別の列に保存して食い違うことを避ける）
- **推定 1RM**：Epley 式（重量 ×（1 + 回数 ÷ 30））で計算する。回数が多いほど誤差が大きくなるため、1〜10回のセットだけを対象にする
- **種目ごとの推移グラフ**：種目を選ぶと、実施日ごとの値を折れ線グラフで表示する（直近3か月・1年・全期間）
  - 重量 × 回数：その日の最大重量・その日の最大の推定 1RM
  - 回数のみ：その日の合計回数・1セットの最大回数
  - 時間・距離：その日の合計時間・合計距離（ランニングはペースも）
- 推移は本人だけが見られる

### 5.5 記録の集計

本人の記録だけを集計し、本人だけが見られる。週は**月曜始まり**、日付は**日本時間**で区切る。

| 集計 | 内容 |
|---|---|
| 週間 | 指定した週のトレーニング日数・総挙上量・運動時間・距離・消費カロリー・部位別のセット数、前の週との比較、曜日ごとの棒グラフ |
| 月間 | 指定した月のトレーニング日数・総挙上量・運動時間・距離・消費カロリー・部位別のセット数、前の月との比較、週ごとの推移グラフ |
| カレンダー | 月のカレンダーに、トレーニングした日の印を付ける。日付を押すとその日の投稿を表示する |

- トレーニング日数は、1日に複数回投稿しても1日と数える
- 集計は表示のたびに SQL で計算する（集計結果を別のテーブルに保存しない）。データが増えて遅くなった場合の対応は将来の課題とする

#### 5.5.1 ランニングの集計

「ランニング」に分類した種目（5.1）のセットを対象に、**週間・月間・年間**で集計する。

| 項目 | 計算のしかた |
|---|---|
| 走行距離 | 距離の合計 |
| 走行時間 | 時間の合計 |
| 平均ペース | **距離を記録したセットの合計時間 ÷ 合計距離**（1回ごとのペースの平均ではない）。1km（マイル表示のときは1マイル）あたりの時間で表示する |
| ベスト記録：最速ペース | その期間で一番速いペースの1回（1セット）。距離の短い記録で極端な値にならないよう、**1km 以上**のセットだけを対象にする |
| ベスト記録：最長距離 | その期間で一番長い距離の1回（1セット） |

- 前の期間（前の週・月・年）と比べて表示する
- ベスト記録を押すと、その記録の投稿を表示する

### 5.6 体重の記録

- 日付・体重（kg、0.1 刻み。lb 表示のときは 0.2 刻み）・体脂肪率（%、任意）を記録する。1日1件まで（同じ日に記録すると上書き）
- 体重の記録は投稿とは別の機能とし、**本人だけが見られる**（タイムラインに流れない）
- 直近3か月・1年の推移を折れ線グラフで表示する

### 5.7 目標設定

| 種類 | 例 | 期間 | 達成率の計算 |
|---|---|---|---|
| 頻度 | 週4回トレーニングする | 毎週／毎月 くり返し | その週（月）のトレーニング日数 ÷ 目標回数 |
| 量 | 月間ランニング 100km、月間総挙上量 50,000kg | 毎週／毎月 くり返し | その週（月）の合計 ÷ 目標値（対象：総挙上量・運動時間・距離。種目・部位で絞り込める） |
| 重量 | ベンチプレス 100kg | 期限つき（期限なしも可） | 現在の自己ベスト ÷ 目標重量 |
| 体重 | 体重 70kg | 期限つき（期限なしも可） | 開始時の体重から目標までの差のうち、どれだけ進んだか |

- 目標は同時に10件まで持てる。100% に達した目標は「達成」とし、達成日を記録して達成済みの一覧に移す（くり返しの目標は、週・月ごとの達成状況を一覧で表示する）
- 達成率は表示のたびに記録から計算する。達成したかどうかの判定は、投稿・体重の記録を保存（作成・編集）したあとに行い、達成したら達成日を保存して通知する（5.9）
- **目標の公開**：目標ごとに公開範囲（公開／フォロワー限定／自分のみ）を選べる。初期値は「自分のみ」。公開した目標はプロフィールに表示し、見られる人は「応援」できる（1人1目標につき1回）
  - **体重の目標は公開できない**（7章：体重は本人以外に見せない）
  - 公開した目標でも、ほかの人に見せるのは達成率と目標の内容だけとし、もとになった記録の値（集計値）は見せない

### 5.8 認証・プロフィール・ユーザー検索・タイムライン

前回の SNS アプリと同じ仕組みとする（ユーザー名・パスワードの規則、JWT による認証、スクロールでの続きの読み込みなど）。違いは次のとおり。

- 新規登録でメールアドレスも入力する（一意。アカウント管理に使う。5.12）
- タイムライン・プロフィールの投稿一覧に、公開範囲と鍵アカウントの判定（5.2）が入る
- 投稿カードに、種目とセットの要約（例：「ベンチプレス 60kg × 10回 × 3セット」）を、見る人が選んだ単位で表示する

### 5.9 通知

| 通知の種類 | 受け取る人 |
|---|---|
| ナイストレーニング | 投稿者 |
| コメント | 投稿者 |
| 返信 | 返信先のコメントを書いた人 |
| フォローされた | フォローされた人 |
| フォローのリクエスト | 鍵アカウントの人 |
| リクエストが承認された | リクエストした人 |
| 目標の達成 | 目標を持っている本人 |
| 目標への応援 | 目標を持っている本人 |

- 自分の操作で自分に通知は送らない（自分の投稿に自分でナイストレーニングを付けたとき、など）
- ナイストレーニング・応援・フォローを取り消したときは、その通知も消す
- 通知を作る処理は、もとの操作（ナイストレーニングなど）の保存が確定したあとに行う。通知を作れなくても、もとの操作は成功として扱う
- 画面には未読の数を表示し、一定の間隔（目安：1分）と画面を開いたときに問い合わせて更新する。通知の一覧を開くと既読にする
- 通知を見るときも閲覧の制御（5.2）に従い、見られなくなった投稿についての通知は表示しない

### 5.10 投稿の検索・ハッシュタグ

- **ひとことの部分一致検索**：日本語の2文字以上の語で探せる
- **ハッシュタグ**：ひとことの中の `#` から始まる語（日本語・英数字、30文字まで）をハッシュタグとして保存する。投稿のハッシュタグを押すと、同じハッシュタグの投稿の一覧を表示する。英字の大文字・小文字は区別しない
- **種目での絞り込み**：選んだ種目を含む投稿だけを表示する
- 3つは組み合わせられる。どの検索も、見てよい投稿だけを、新しい順に表示する

### 5.11 テンプレート・前回の記録の複製

- **テンプレート**：名前・種目・セット（重量・回数などの値を含む）を保存する。20件まで。本人だけが使える
  - 記録の作成画面でテンプレートを選ぶと、種目とセットを入力した状態にする（実施日・ひとこと・画像は入れない）
  - 投稿の詳細画面から、その記録をテンプレートとして保存できる
- **前回の記録の複製**：自分の投稿から「この記録を複製」を選ぶと、種目とセットを入力した状態で作成画面を開く。実施日は今日にする
- 自分専用の種目を消した場合、その種目を含むテンプレートからはその種目を外す

### 5.12 アカウント管理

| 機能 | 決まりごと |
|---|---|
| メールアドレスの確認 | 登録したとき・メールアドレスを変えたときに、確認用のリンクをメールで送る。リンクの有効期限は24時間。確認するまで、画面に案内を表示する |
| パスワードの変更 | 今のパスワードを入力して変更する |
| パスワードのリセット | メールアドレスを入力すると、再設定用のリンクを送る。リンクの有効期限は30分で、1回だけ使える。**入力したメールアドレスが登録されているかどうかに関係なく、同じ応答を返す**（登録の有無を知られないため） |
| 退会 | パスワードを入力して退会する。本人の投稿・画像・ナイストレーニング・コメント・フォロー・通知・体重・目標をすべて削除する（ほかの人の投稿に付けたコメントも消える） |

- パスワードを変更・リセットしたときは、すべての端末のログイン（リフレッシュトークン）を無効にする
- 確認用・再設定用のトークンは、ハッシュにして保存する

### 5.13 消費カロリー

消費カロリーの**目安**を、次の式で計算する（式は国立健康・栄養研究所「改訂版 身体活動のメッツ（METs）表」にもとづく）。

> 消費カロリー（kcal）＝ METs × 体重（kg）× 時間（時間）× 1.05

| 部分 | METs | 時間 |
|---|---|---|
| 有酸素（時間・距離の種目） | 種目の METs。ランニングで距離がある場合は、ペースに応じた METs | そのセットの時間 |
| 筋トレ（重量 × 回数・回数のみの種目） | 投稿に含まれる筋トレの種目の METs を、セット数で重みづけた平均 | トレーニング時間 − 有酸素の時間の合計 |

- 体重は、実施日以前で一番近い日の体重の記録を使う。体重の記録が1件もないときは計算せず、体重の記録を勧める表示を出す
- トレーニング時間を入力していない投稿では、筋トレの部分を計算しない（有酸素の部分だけを表示する）
- 消費カロリーは**本人だけが見られる**（消費カロリーと METs・時間が分かれば体重を逆算できるため。7章）
- 投稿の詳細と、週間・月間の集計に表示する。値は「目安」であることを画面に書く

### 5.14 単位の切り替え

- ユーザーごとに、重量（kg／lb）と距離（km／マイル）の単位を設定で選ぶ。初期値は kg・km
- 選んだ単位で入力し、表示する（自分の記録もほかの人の投稿も、見る人の単位で表示する）。ペースは「1km あたり」または「1マイルあたり」で表示する
- 保存は常に kg・km（5.1）。集計・自己ベスト・目標の判定も kg・km で行い、表示するときに換算する
- 換算：1lb ＝ 0.45359237kg、1マイル ＝ 1.609344km

## 7. 非機能要件

次の段階で [非機能要件](./non-functional-requirements.md) にまとめる。前回の SNS アプリの非機能要件（性能・セキュリティ・保守性など）を引き継ぎ、次を加える。

- **閲覧の制御の漏れがないこと**：公開範囲・鍵アカウントの判定を API の全ての入口（一覧・詳細・検索・ナイストレーニング・コメント・通知・画像の URL）で行い、テストで確かめる
- **集計の性能**：1年分（約300件の投稿・約1万セット）の記録があっても、週間・月間・年間の集計画面と種目ごとの推移が規定の時間内に表示されること（具体的な数値は非機能要件で決める）
- **検索の性能**：投稿が増えても、ひとことの部分一致検索が索引を使って行われること
- **画像の表示の速さ**：アップロードの前に縮小し、同じ画像の URL は一定の時間変わらないようにしてブラウザのキャッシュを効かせる
- **日付の扱い**：実施日は日付型（時刻・タイムゾーンなし）で持ち、週・月・年の区切りは日本時間で計算する
- **体重などの健康に関わる情報**（体重・体脂肪率・消費カロリー・体重の目標）は本人以外の API の応答に含めない
- **アカウントの安全**：パスワードのリセットで、メールアドレスが登録されているかどうかを知られない。確認用・再設定用のトークンは、有効期限つき・1回限り・ハッシュで保存する。メールの送信の回数に上限を設ける
- **単位の換算で値がずれないこと**：lb・マイルで入力した値が、表示し直したときに入力した値に戻ることをテストで確かめる

## 8. データ構造・ER図

次の段階で [データ構造・ER図](./database.md) にまとめる。現時点で想定しているテーブルは次のとおり。

| テーブル | 内容 |
|---|---|
| users | ユーザー（前回の内容に、メールアドレスと確認日時・鍵アカウントかどうか・単位の設定を加える） |
| refresh_tokens | ログイン状態を保つためのトークン（前回と同じ） |
| email_verification_tokens | メールアドレスの確認用のトークン（ハッシュ・有効期限） |
| password_reset_tokens | パスワードの再設定用のトークン（ハッシュ・有効期限・使用日時） |
| exercises | 種目（名前・部位・記録方式・METs・ランニングかどうか）。最初から用意された種目と、ユーザーが追加した種目（作成者を持つ） |
| workouts | トレーニング記録（投稿）。実施日・ひとこと・トレーニング時間・公開範囲 |
| workout_images | 投稿の画像（S3 のキー） |
| workout_exercises | 投稿に含まれる種目と並び順 |
| workout_sets | 種目ごとのセット（重量（kg、小数第3位まで）・回数・時間（秒）・距離（km、小数第3位まで）と並び順） |
| hashtags | ハッシュタグ（小文字にそろえた名前で一意） |
| workout_hashtags | 投稿とハッシュタグの多対多 |
| workout_templates | テンプレート（名前） |
| template_exercises・template_sets | テンプレートの種目とセット（workout_exercises・workout_sets と同じ形） |
| likes | ナイストレーニング（users と workouts の多対多） |
| comments | コメント（返信のときは返信元のコメントを持つ） |
| follows | フォロー（users 同士の多対多。承認待ち・承認済みの状態を持つ） |
| notifications | 通知（受け取る人・種類・操作した人・対象・既読日時） |
| body_records | 体重・体脂肪率の記録 |
| goals | 目標（種類・期間・目標値・対象の種目や部位・達成日・公開範囲） |
| goal_cheers | 目標への応援（users と goals の多対多） |

- 「投稿 → 種目 → セット」は親子関係とし、投稿を削除すると種目・セット・画像・ハッシュタグとの関連・ナイストレーニング・コメントも消える
- ナイストレーニング数・コメント数・自己ベスト・推定 1RM・集計値・ペース・消費カロリー・達成率は列として持たず、表示のたびに計算する
- ユーザーを削除（退会）すると、そのユーザーに関係する行をすべて消す（外部キーの `ON DELETE CASCADE`。S3 の画像は保存の確定後に別に消す）

## 10. 未決定事項

- **メールアドレスの確認前に使える範囲**：確認するまで投稿などを制限するか、案内を表示するだけにするか（5.12 は「案内だけ」としている）
- **独自ドメインを取得するか**：画面は CloudFront の URL でも HTTPS にできる。ただし、SES でメールを確実に届けるには、送信元として独自ドメインを使うのが望ましい（[技術スタック](./tech-stack.md)）
- **種目の初期データ**：最初から用意する種目の一覧（部位ごとに何種類用意するか）と、それぞれの METs
- **他人のプロフィールに集計を見せるか**：MVP では集計は本人だけとしたが、「今月 12 日トレーニング」程度の公開情報をプロフィールに出すか
- **通知の保存期間**：古い通知をいつ消すか
- **退会したユーザーのユーザー名**：すぐにほかの人が使えるようにするか

## 11. 開発の進め方

前回の SNS アプリと同じ進め方とする。

1. 要件定義（この文書）→ 機能要件・画面仕様・非機能要件・データ構造・API 設計・技術スタック・テスト計画の詳細ドキュメント
2. モックアップで画面を確かめる
3. GitHub の Issue → ブランチ → PR の流れで、テスト駆動（TDD）で実装する
4. AWS へのデプロイ、パフォーマンステスト

範囲が広いため、実装は「前回の SNS アプリと同じ部分（認証・投稿・いいね・コメント・フォロー）→ 記録と集計 → 目標 → 通知・鍵アカウント・検索・テンプレート → アカウント管理・単位・消費カロリー」の順に、動く状態を保ちながら進める。
